# Ocean Desk 2.0 — 41차 단계별 배포 및 긴급 중지·복구 검증

**대상:** 기존 Supabase OCEAN DESK 프로젝트 `gozsvzkqhpmimadtgfie`. 이 문서는 실행 승인이나 실제 운영 배포 기록이 아닙니다. 41차 SQL은 **GitHub Actions의 일회용 PostgreSQL 테스트 환경 전용**입니다.

## 1. 적용 전 필수 통과 조건
1. **별도 테스트 환경 확보와 비용 확인**: 새 Supabase 프로젝트/브랜치를 만들기 전 현재 무료 한도 및 예상 비용을 확인하고 명시적 승인을 받습니다.
2. 운영 DB 전체 스키마(테이블·인덱스·FK·RLS·GRANT·트리거·함수)와 실데이터의 **복구 가능한 백업**을 확보하고, 별도 환경에서 복원 성공 여부를 검증합니다. GitHub의 테스트 샘플은 실제 백업이 아닙니다.
3. 운영과 다른 테스트 데이터로 마이그레이션과 RLS 검증을 실행하고, 정식 배포 시점에 기존 사용자의 서비스 영향과 되돌리기 제한을 공지합니다.
4. 개발 브랜치의 신규 인증 설정은 기본 비활성, 서버 `service_role` 등 비밀 키는 브라우저·저장소에 배포하지 않습니다.
5. Google OAuth 테스트는 승인된 HTTPS Preview 도메인/리디렉션을 확보한 다음 테스트 계정만 사용합니다.

## 2. 제안 배포 순서 (운영 미실행)
1. **기존 서비스 동결**: 운영 코드, DB와 관련 리소스 상태 및 복구 기준을 먼저 고정합니다.
2. **신규 스키마 추가**: `od_regions`, `od_environments`, `od_wallets`, `od_owned_environments`, `od_reward_claims`, `od_travel_draws`와 서버 검증 집중/광고 테이블을 기존 카페·좌석 테이블 변경 없이 추가하는 계획을 별도 테스트 환경에서 검증합니다.
3. **RLS + 역할별 권한**: 계정 데이터는 `authenticated`에게 본인 것만 SELECT, 브라우저에 직접 보상 쓰기 권한을 부여하지 않습니다. 민감한 서버 함수는 비공개 서버에서만 호출할 수 있도록 승인된 내부 호출 경계를 확인해야 합니다.
4. **서버 함수 및 Edge Functions**: 재시도 중복 처리·지갑 초기화·25/50분 집중 시작·취소·완료·보상 이벤트 검증·여행 추첨을 테스트 사용자 두 명으로 재현합니다. 서버 비밀은 브라우저에 공개하지 않습니다.
5. **안전한 테스트 로그인**: 운영 로그인 설정과 구분된 테스트 환경에서 Google OAuth 및 타 사용자 접근 차단·기기 간 동기화를 검증합니다.
6. **코드 Preview 검증**: 테스트 DB/인증에만 연결한 Preview에서 회귀 테스트와 PC/모바일 실제 사용 테스트를 완료합니다.
7. **별도 승인 후 단계적 운영 활성화**: 기능 플래그를 기본 OFF로 두고 상태 확인 후 소규모로 켭니다. `main` 머지/운영 Vercel 배포는 별도 승인 전 금지입니다.

## 3. 41차 격리 테스트로 확인하는 긴급 중지
- `tests/server/feature-gate-stop.sql`: **서버 기능 RPC 7개에 대한 `service_role` 실행 권한만 REVOKE**합니다.
- `tests/server/feature-gate-resume.sql`: 해당 7개 권한을 GRANT로 복원합니다.
- `tests/server/test_feature_gate.py`: 중지 전/중지/복원 후 임시 DB 15개 테이블의 레코드 수, RLS, 공개·인증 역할의 RPC 거부 상태를 비교합니다.
- **중요:** 이미 시작된 트랜잭션, DB 슈퍼유저/소유자 권한, 별도 테이블 직접 접근, 운영 Edge Function 요청까지 즉시 차단하는 메커니즘은 아닙니다. 실제 장애 시에는 우선 **애플리케이션 기능 플래그를 OFF**, Edge Function 요청·서버 비밀 경로 차단 등 운영 통제를 병행해야 합니다.
- `REVOKE/GRANT`는 데이터 마이그레이션 복원이 아닙니다. 데이터가 삭제·수정된 사고라면 사전 검증된 백업/PITR 복원 계획이 필요하며, 운영 DB 복원은 별도 승인 사항입니다.
- 이 SQL은 승인된 운영 변경 스크립트가 아니며 테스트용 예시입니다. 운영에 그대로 실행하지 마세요.

## 4. 실패 시 의사결정
| 상황 | 즉시 대응 | 데이터 처리 |
|---|---|---|
| 로그인/리디렉션 실패 | 신규 로그인 플래그 OFF, 운영 카페 기능 유지 | DB 변경 금지, 로그 확인 |
| RLS/권한 문제 | 서버 신규 보상 기능 OFF, 테스트 중단 | 원본 상태 비교 및 보안 재검토 |
| 중복 지급/티켓 차감 오류 | 보상·추첨 엔드포인트 OFF, 비밀 접근 차단 | 임의 잔액 수정 금지, 거래 로그 검토 |
| 신규 스키마 충돌 | 마이그레이션 진행 중단 | 롤백 가능 DDL과 데이터 이관 여부 확인 |
| 데이터 손상 | 쓰기 차단 및 복구 계획 개시 | 백업/PITR 복원 가능성 확인 후 승인 처리 |

## 5. 검증의 한계 및 현재 상태
- 기존 카페·좌석·집중 테이블의 대표 스키마와 모의 사용자/보상 기록만 사용. 운영 Supabase DB에는 41차 SQL을 실행하지 않았습니다.
- 자동화는 승인 없는 실제 백업 복원, 운영 계정 OAuth, 서비스 비밀 키 테스트를 하지 않습니다.
- 실제 운영 계정 동기화와 서버 검증 광고/보상은 여전히 미활성.
- 새 계정/프로젝트/브랜치를 생성하거나 유료 플랜으로 변경하지 않았습니다.
- **완료 조건:** 일회용 PostgreSQL에서 중지/복원 시 함수 권한만 바뀌고 모든 테스트 테이블의 레코드 수와 RLS가 보존되는 자동 검사가 성공해야 합니다.
